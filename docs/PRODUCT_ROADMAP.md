# manageable-mcp v2 产品路线图

> 本文件迁移自旧仓库 `doc/ROADMAP.md`。三个产品目标、验收标准、四阶段路线和工程约束均保留，
> 并按 v2 当前实现补充状态。状态截至 2026-11-28，对应包版本 `0.2.0` 和技术路线图 0.8 阶段。

## 状态口径

- **已完成**：v2 代码已实现，并有仓库内测试或 smoke/E2E 覆盖。
- **部分完成**：已有可工作的基础能力，但目标中的规范、评测或完整流程尚未交付。
- **未开始**：没有对应实现；已有相邻能力只能算基础，不能算完成。

本文件不会把设计稿、零散开关或旧仓库成果计为 v2 已完成。

## 规划原则

- 保持客户端无关；stdio 与 HTTP 共享同一配置、分组和权限语义。
- `servers.json` 是唯一配置事实来源，不建立第二套服务器数据库。
- 下游连接按需建立，市场、管理 UI、后台监控等可选功能不得成为核心代理的启动前提。
- v2 是破坏性重写，不恢复旧品牌兼容层；旧配置迁移见
  [CONFIG_MIGRATION.md](./CONFIG_MIGRATION.md)。

## 三个开发目标

### 目标一：Agent 接入与工具感知（P0，部分完成）

**目标状态：部分完成。** 接入基础设施已经可用，目录描述规范和客户端一键接入尚未完成。

| 工作项 | 状态 | v2 现状与缺口 |
| --- | --- | --- |
| Stdio 独立接入 | 已完成 | 支持直接运行 stdio MCP server，使用本地配置和当前用户信任边界 |
| 共享运行时 | 已完成 | `--attach <url>` 将 stdio 客户端桥接到运行中的 HTTP 守护进程；桥接进程不读取 `servers.json`、不启动下游服务器 |
| stdio/HTTP 共享语义 | 已完成 | 两种 transport 共用配置模型；分组过滤、四个元工具、权限和结果整形走同一管理器 |
| MCP 目录摘要基础 | 已完成 | `list_servers` 描述可嵌入已启用服务器名称和完整描述；支持 `maxDescriptionChars`、`maxCatalogChars` 显式告警，不静默截断 |
| Server 目录描述规范 | 部分完成 | 已有 [撰写规范和评测集](./CATALOG_GUIDE.md)，尚缺真实 Agent 评测结果 |
| 一键接入 | 部分完成 | 已实现四种客户端的配置定位、注入、更新、移除、备份和回滚；实际客户端验收见 [接入文档](./CLIENT_INTEGRATION.md) |
| 本地信任边界 | 已完成 | stdio 以启动它的操作系统用户为信任级别；HTTP 的 bearer、Host/Origin 和回环限制独立执行 |

**原验收标准与当前状态**

- [x] stdio 与 HTTP 的工具调用和分组行为一致；已有 smoke/E2E 覆盖。
- [x] 共享模式不重复启动下游服务；`--attach` 只转发协议请求。
- [ ] 代表性任务中 Agent 能依据目录正确选择 MCP；评测集已建立，尚未取得真实 Agent 结果。
- [ ] 已支持客户端完成一键接入、验证及回滚测试；隔离流程已测，OpenCode 和 Cursor 的真实客户端连接未完成验证。

### 目标二：MCP 管理与市场生态（P1，未开始）

**目标状态：未开始。** v2 的管理 CRUD、分组、权限、OAuth 和状态端点可以作为复用基础，
但它们不构成市场或自动安装流程。

- **MCP 市场**：对接官方 MCP Registry 等来源的数据源适配层、搜索、浏览、安装、更新和卸载均未开始。
- **自动化配置**：安装依赖、启动参数、环境变量、API Key、OAuth 授权的前置展示和自动化流程均未开始。
- **管理闭环**：市场条目自动进入现有 `servers.json`、管理面板、分组、权限和状态体系尚未实现；
  当前只有手动服务器 CRUD 和检测。

市场目标只管理外部 MCP 的发现、安装和本地配置，不改变 v2 自身“不发布到 npm/PyPI/Docker/Homebrew”
等非目标。

**原验收标准与当前状态**

- [ ] 从市场搜索到安装、配置、授权、调用、更新和卸载形成完整流程。
- [ ] 失败可诊断、可回滚。
- [ ] 市场模块关闭后不影响已配置 MCP 的使用。

### 目标三：资源分级与按需运行（架构设计 P0，实现 P2，未开始）

**目标状态：未开始。** v2 已有清晰模块边界，管理面板和健康探测也分别可关闭，
但没有统一的“精简/标准/完整”模式契约、生命周期控制或资源测量。零散开关不能算运行模式分级。

| 功能 | 精简模式 | 标准模式 | 完整模式 |
| --- | --- | --- | --- |
| MCP 代理与渐进式披露 | 启用 | 启用 | 启用 |
| 下游服务按需启动 | 启用 | 启用 | 启用 |
| Web 管理界面 | 关闭 | 启用 | 启用 |
| 后台健康监控 | 关闭 | 启用 | 启用 |
| MCP 市场 | 关闭 | 按需加载 | 启用 |
| 自动更新检查 | 关闭 | 关闭 | 启用 |
| 运行统计与诊断 | 必要日志 | 基础 | 完整 |

必要的权限校验、认证和错误处理不得因模式降级而削弱。模块加载策略、运行时切换方式及资源预算
仍需在实施阶段设计并验证。

**原验收标准与当前状态**

- [ ] 三种模式均保留核心 MCP 功能；尚未实现模式。
- [ ] 关闭的模块不执行周期性任务；尚无统一模块生命周期。
- [ ] 用启动时间、空闲内存、CPU、后台网络请求和调用延迟实测资源控制效果；尚未测量。

## 工程约束

1. 以 v2 当前代理核心为稳定基线。后续功能不得破坏四个元工具、渐进式披露、
   工具缓存和懒加载契约；不为新功能重写已验证的核心。
2. 保持 `servers.json` 单一事实来源，不建立独立服务器数据库；新增功能优先通过清晰接口
   与核心解耦。原“保持现有配置兼容”在 v2 中只指 v2 配置，不包含旧仓库兼容层。
3. 不以额外常驻进程、轮询或后台服务作为可选功能的默认实现前提；关闭的模块应释放监听器、
   定时器和资源，而不是只隐藏 UI。
4. 保持下游调用权限和协议结果保真；秘密不得进入日志、错误文本或测试快照。
5. 每阶段开始前审查源码与现状，并保留设计决策、执行指令、实现/测试证据和验收结论四类记录。
   旧项目的 `workdocs/` 目录未迁入 v2；开始新阶段前应先确定等价记录位置，不得伪造历史记录。
6. 阶段间独立提交；明确已通过、失败、阻塞和未验证项，不以路线图勾选代替真实验收。
7. 性能阈值基于基线实测确定，不预设在本路线图中。

## 核心架构决策

从第一阶段起采用模块化、可按需加载的设计，而不是等功能齐备后再做轻量化改造。
v2 的 `src/config`、`src/mcp`、`src/transports`、`src/admin`、`src/oauth` 和 `src/client`
边界已经体现这一方向；三种运行模式仍需在此基础上实现，不能仅凭现有目录结构宣称完成。

本文件是产品路线，不是详细实施指令；共享运行时的后续扩展、客户端适配细节、市场协议和资源预算
仍需在对应阶段设计、实现并验证。
